# 部落格技術示意圖生成

這份規範來自一次代價高昂的實作：九張圖、四輪重生、一次上線後回滾。裡面每一條
規則都對應一個實際踩過的坑，不是理論推導。**開始寫 prompt 前請先讀完「已驗證的
教訓」那一節**，那裡的東西違反直覺，靠自己重新推導會付出同樣的學費。

## 生成路徑

```bash
codex exec --skip-git-repo-check -s workspace-write "$(cat prompt.txt)" < /dev/null
```

`codex features list` 中的 `image_generation` 為 stable。注意：

- **必須關閉 stdin**（`< /dev/null`），否則 codex 會停在等待輸入。
- **沒有任何 API 參數可調。** quality、size、background、reference image 全部由
  codex 決定，只能在 prompt 裡用文字要求比例。網路上強調 `quality="high"`、
  `background="transparent"`、`input_fidelity` 的教學一律不適用。
- codex 會自行迭代數次再交件，而且**它宣稱達標時經常沒有達標**。生成後一律
  自己量，不要相信它的自述。

## 已驗證的教訓

這幾條都有對照組，不是猜測。

### 空間指令要寫成可驗證的斷言

模型執行語言類指令（文字內容、標籤、標點）幾乎都對，執行空間類指令
（位置、對齊、相對大小）失敗率很高。

描述式寫法會失敗，斷言式寫法會成功——同一張圖的前後兩版是直接對照：

```
✗ 「刻度畫在灰段與藍段的交界」
✓ 「刻度線必須與灰色塊右邊緣、藍色塊左邊緣落在同一條垂直線上」

✗ 「卡片畫得大一點以示強調」
✓ 「這張卡片的高度必須是其他五張的 1.3 倍以上」

✗ 「文字過長時換行，不要縮字」          ← 實測失敗，模型仍然縮字
✓ 「這行文字必須斷成兩行：第一行『依 centroid_pipeline』，第二行『投影並算中心點』」
```

斷言式的附加好處是驗收標準與 prompt 是同一句話，沒有解釋空間。

### 但斷言會被 Goodhart 掉

寫出可量測的目標之後，模型會用最省事的方式命中那個數字，而那個方式可能正是
你不要的。

實例：斷言「卡片左右邊緣距畫布不超過 4%」被完全滿足，做法是把卡片拉成寬扁空盒，
文字只佔卡片寬度的 32–49%，右側全空。驗收時量「非白像素佔畫布 94.1%」判定通過
——但卡片底色本來就不是白的，那個數字量到的是**卡片有多寬**，不是**內容有多滿**。

**指標要量最終目的，不要量代理量。** 用 `scripts/verify_diagram.py`，它同時量
非白區域與深色墨跡，並逐列比對兩者以抓出寬扁空盒。

### 改構圖前先確認畫框比例撐得住

砍掉內容卻維持原比例，多出來的空間只會變成外側白邊或卡片內空白，兩者都更糟。

那次的具體情況：縱向八段管線 ＋ 右側註解欄，在 16:9 裡是平衡的。把右欄砍掉
（理由是它重複了內文）之後，模型第一版把卡片置中留下 46% 側邊白邊，第二版把
卡片拉滿留下 60% 卡片內空白。兩版是同一個錯誤的兩種形態。

**內容形狀決定畫框比例**：縱向流程要 4:3 或 3:2，橫向數線要 16:9 或更寬。
不要用砍內容去遷就比例。

順帶一提：圖表複述內文是正常功能，不是缺點。「這欄重複了上面那段話」不是砍掉
它的理由。

### 長英文識別字會拼錯

`centroid_pipeline` 曾被生成為 `centprid_pipeline`。機率低於空間類指令，但會發生。

**中文也會出錯，只是錯法不同。** 不是拼錯，是選到異體字：一張圖的說明文字把「改為」
生成成「改爲」。這類錯誤不會觸發任何拼字直覺，要逐字比對才看得出來。有把握會出現
異體字的字（為／爲、裡／裏、臺／台），在 prompt 裡直接指定字形：

```
其中的「為」必須寫成「為」，絕對不可寫成異體字「爲」。
```

**把關鍵識別字用直引號包起來**，GPT Image 2 對引號內文字會精準渲染：

```
第 5 張卡片的第一行文字逐字為 "apply_country_centroids"
```

### 對比圖要固定變因

左右對比圖的說服力來自「只有一個東西不一樣」。模型不會自己維持這件事：一張點位密度
對比圖，左右兩個面板各自生成了不同形狀的地圖，於是讀者無法判斷差異來自點位還是來自
地圖本身，對比失效。

寫成斷言：

```
右面板的地圖必須與左面板是同一張地圖：多邊形的形狀、數量與位置在左右兩個面板
必須完全相同，像是同一張圖複製了兩份。
```

同一張圖裡要出現兩次的元素（兩個相機、兩組島嶼、兩份地圖），一律補一句「形狀必須
完全相同」，否則會各畫各的。

### 密度要給數量，否則會變網點材質

「密集地散布大量圓點」被執行成規則排列的半色調圖樣，把底下的行政區界完全蓋掉——
點位密度圖的重點正是「每個區塊裡面有幾個點」，蓋掉邊界等於把資訊拿掉。

給每個容器的數量範圍，並且把「底下的東西要看得見」寫成獨立條件：

```
每一個多邊形內部各放 6 到 10 個圓點。
圓點之間必須留有空隙，多邊形之間的白色分隔線必須仍然清楚可見，不可被圓點蓋住。
圓點不可密到變成規則的網點材質或半色調圖樣。
```

### 地圖類圖的裝飾要另外禁

卡片類的裝飾禁令擋不住地圖：島嶼上會自己長出山脈、樹叢、草地，海面上會出現船與雲。
判準跟圖示一樣——換掉會不會損失資訊——但要在【文字限制】段另外列名：

```
島嶼上不可畫山、樹叢、草地或任何地貌裝飾，只有純色形狀與外框。
不要出現船、椰子樹、雲。
```

### 規則本身會誤傷

「標點一律全形」本意是針對中文標點，結果把檔案路徑 `meta_data/<國碼>_geodata.csv`
的斜線也變成全形。

**每加一條規則都要想它會誤傷什麼**，不是條款越多越安全。全形規則要帶例外：

```
中文標點用全形。
英數識別字內的底線、斜線、數字一律保持半形，不可轉為全形。
```

### 重生會引入新缺陷，達標就停

四輪重生裡有三輪在修好舊問題的同時弄壞新東西：拼字錯、全形斜線、步驟編號消失。
缺陷注入率超過五成。

**但這個數字有適用範圍。** 那四輪都是對同一張圖反覆迭代，每輪只改局部指令，模型在
沒被提到的部分自由發揮，於是弄壞別的地方。後來用完整 prompt 從零重生兩次（同一張
流程圖的無圖示版與圖示版），文字與識別字全對，一次到位，沒有注入任何缺陷。

所以區分兩種操作：**局部迭代危險，完整 prompt 重生不危險。** 要改一張圖，重寫完整
prompt 再生一張，不要在既有結果上打補丁。

至於值不值得重生：語意正確的圖不必為了美感重做，但「可讀性」不是美感。上面圖示那條
就是靠一次受控重生翻案的。

### 百分比位置斷言會落空

「必須落在畫布高度的 50%」這類斷言，兩次生成分別跑出 53.0% 與 55.5%，同方向偏移。
對齊類斷言（「必須與 X 落在同一條垂直線上」）也只做到差 21px。

推論：模型能執行**相對關係**（誰在誰左邊、誰接誰），但對**畫布絕對座標**沒有可靠
的控制力。所以位置需求盡量寫成元素之間的相對關係，不要寫成畫布百分比；真的需要
精確座標時，接受偏差或改用向量工具重畫。

### 用量的，不要用看的

這條讓整個系列白跑了四輪並回滾。

一張圖被目測判定「刻度偏離交界約 90px、屬於語意錯誤」，據此重生四輪。實際量下來
偏差是 1px——原圖從頭到尾都是對的。目測是從 200% 裁切估位置，估錯了。

反過來也發生：目測「字變大了一倍」的版本，量出來只大 5%。

凡是位置、比例、覆蓋率，一律跑腳本。而且**量到的數字要用 `--probe` 畫回圖上
確認**，因為偵測邏輯可能抓到邊框而不是你以為的那條線。

### 審查前先確認你看的檔案就是線上的檔案

暫存目錄裡的檔案會被後續作業取代。曾有一個「雙逗號」缺陷被回報並排入修正，
實際上線上版本的標點是正確的——審查對象是一個已經被換掉的舊檔。

**動手前先 `curl` 線上圖比對 md5。**

## Prompt 結構

依序寫這幾段。內容段放最後，因為前面的約束會影響它的解讀。

```
生成一張技術部落格用的<類型>圖，存成 ./<檔名>.png，<比例>。只生成圖片，不要寫程式碼。

【風格】   ← 見下方 style lock，逐字複製不要改寫
【構圖】   ← 硬性尺寸斷言（比例、邊距、色帶高度）
【內容】   ← 每個元素的位置、顏色、逐字文字
【位置】   ← 對齊類斷言，寫成「必須與 X 落在同一條垂直線上」
【文字限制】← 語言、標點、半形例外
```

## Style lock

逐字複製，不要改寫措辭。措辭不一致會導致同系列的圖跑出不同風格——曾有一張因為
風格段的措辭與其他張不同而跑成厚重單色藍 3D。

```
【風格】（本段原封不動使用）
淺色乾淨的技術插畫，白色至近白背景。
卡片白底或極淡色底、圓角、細彩色邊框、非常輕的陰影；標題文字用對應的邊框色，內文深灰。
圖示只能畫具體實體（容器、資料庫、檔案、照片、地點），不可畫動作或情緒的隱喻。
圖示一律單色線稿，線條顏色與該卡片的邊框色相同，線寬與卡片邊框相同，正面平視不用等角視角。
一張圖裡所有圖示的高度必須相同，並且放在該卡片標題文字的正左側。
不可使用品牌 logo，不可畫成全彩、立體、有陰影或有漸層的圖示。
箭頭上、背景中、卡片外一律不放圖示。
不使用帶微光的貝茲曲線。
配色一律低飽和淡色：主色淡藍 #6B9BD1、強調珊瑚 #FF8A80、判定淡紫 #9C27B0、
成功淡綠 #54D62C、警示琥珀 #FFC107、中性淡灰。
主流程箭頭與強調用的 badge 允許較高飽和度以建立視覺落點，其餘元素維持低飽和。
不要厚重 3D 浮雕、不要高飽和單色塊、不要漸層高光。
```

### 圖示：名詞可以，動詞隱喻不行

這一條改過。先前的規則是「一律不放圖示」，判準是「這個圖示換掉會不會損失資訊」。
那個判準只衡量圖示作為**內容**的價值，漏掉它作為**索引**的功能：讀者掃過一張圖時
先靠形狀分區塊，再回頭讀文字，純文字圖等於逼每個人一開始就逐字閱讀。

實測（機制篇流程圖，同一份 prompt 只改圖示變因，兩版對照）：加上圖示的版本在 799px
下仍然一眼看得出「方塊＝容器、圓柱＝資料庫、相框＝上傳、圖釘＝位置」，可讀性明顯較好，
而且沒有把 AI 味帶回來。

真正的 AI 味來自兩件被混在一起的事：

**指涉動詞的圖示。** 魔法棒代表 `enhance`、掃把代表 `cleanup`、放大鏡配地球代表
最近鄰查詢、✨ 代表「這裡很棒」——這些跟系統裡的任何實體都沒有對應關係，是 Canva
範本的長相。指涉名詞的則相反：卡片講容器就畫容器、講資料庫就畫圓柱，看一眼就知道
區塊在說什麼。

**畫法。** 舊圖的 AI 味有一大半不是圖示本身，是它們被畫成全彩立體 stock logo，配上
漸層高光與發光曲線。同一個資料庫符號畫成跟邊框同色的單色線稿、尺寸統一、固定放在
標題左側，觀感完全不同——技術文件（Stripe、Vercel）就是這樣做的。

避開品牌 logo，用通用符號。不是因為 logo 不準，是因為 GPT Image 2 畫 logo 時容易
滑回全彩立體版本，而且圓柱對任何開發者都等於資料庫，不需要指名 PostgreSQL。

**這條規則改過，代表 style lock 也改過。** 同一系列裡混用新舊 lock 會出現風格漂移，
要嘛整個系列一起重生，要嘛整個系列都不動。

### 圖示在 prompt 裡怎麼寫

【內容】段裡逐張卡片指定，寫成斷言：

```
標題文字正左側放一個單色線稿的圓柱形資料庫圖示，珊瑚色。
所有圖示的高度必須都是 100 px。
圖示總數必須正好是五個，分別在「A」「B」「C」「D」「E」五張卡片上。
```

指定總數與清單有效，兩次生成的圖示數量與位置都正確。高度一致只寫「必須相同」無效，
實測跑出 81 到 106 px（相差 24%），要給具體數字。

## 驗收流程

生成後依序做完，不要跳步。

```bash
python3 .claude/skills/blog-diagram-generation/scripts/verify_diagram.py \
    OUTPUT.png --render-dir /tmp/preview
```

1. **逐節點對照** prompt，確認沒有多出來也沒有漏掉的元素
2. **逐連線對照**：每條箭頭的起點、終點、線型（實線／虛線）、顏色
3. **跑腳本**，看深色墨跡覆蓋率與稀疏列比例
4. **位置類斷言用 `--probe` 逐條核對**：把量到的座標畫回圖上確認
5. **識別字放大 200% 逐字比對**，中文標點確認全形、路徑斜線確認半形
6. **看 799px 與 540px 預覽**，確認最小字級與 badge 可讀
7. **與同篇其他圖並排**，確認風格一致

第 4 步是最容易偷懶而最常出錯的。

### 整批稽核外包給便宜模型

一次要檢查一整個系列的配圖時，逐張讀圖很吃 context。實測可行的做法：把圖先 `curl`
下來放同一個目錄，開 Sonnet 子代理，給它三樣東西——本檔的 style lock 段落、圖片的
絕對路徑清單、以及該系列已知的事實清單（哪個技術名詞是對的、專案不處理什麼）。要求
它逐張輸出「風格判定／內容判定／拼字與全半形／結論」四個欄位，並禁止它推測或生成圖片。

回報裡任何要當成行動依據的結論，自己開圖確認過再用。實測子代理的判讀正確，但那是
抽查驗證過才知道的。

## 部落格整合

- **圖片走 Cloudflare R2**，不在 repo 裡：
  `https://cdn.rxchi1d.me/inktrace-files/engineering/<slug>/<檔名>.png`
- **沒有 lightbox。** 主題的 `render-image.html` 只對本地圖片輸出 `data-zoom-src`；
  遠端 URL 命中 `$isRemote` 走 `RenderImageSimple`，圖片點不開。所以顯示尺寸就是
  最終尺寸，可讀性沒有第二次機會。
- **顯示寬度 = 888px × 圖片的 width 百分比。** 容器 `.max-w-prose-xl` 為 90ch ≈ 888px，
  這個數字要用 `getBoundingClientRect()` 量，截圖像素會因為截圖工具縮放而算錯。
  常見值：`width:90%` → 799px、`width:80%` → 710px、`width:70%` → 622px。
  驗收預覽要用該張圖自己的顯示寬度，不要一律套 799px。
- **CDN 快取 `max-age=31536000`**（一年）。更新後如果看起來沒變，先確認是不是
  快取：`curl` 下來比 md5，再決定要不要 purge。實測一次：覆蓋同一路徑後立刻 `curl`，
  拿到的就是新檔的 md5，沒有卡快取。所以先量再擔心，不要預設要 purge。
- **覆蓋前先備份**，本地與 R2 各一份，並驗證備份的 md5 而不只是檔案大小。
  R2 備份放 `inktrace-files/_backup/<YYYYMMDD>/<原路徑>`，不要在文章目錄裡放
  `xxx-backup-日期.png`——那種檔案會留在原地變成沒人認得的孤兒。

## 待驗證的假設

以下是合理推測但**沒有對照組**，不要當成規則使用，用到時請留意結果：

- 圖示缺口的處理方式。指涉動詞的卡片（例如「最近鄰查詢」）依規則不能放圖示，於是在
  一整排都有圖示的卡片中間看起來像個空洞。目前選擇接受這個空洞，但沒有對照組證明
  它比「破例放一個隱喻圖示」更好。
- 單張圖的文字區塊不超過 8 個。推測依據是一張有 12 個區塊的圖出現排版崩壞，
  但沒有做過控制變因的比較。
- 視覺層級的具體手法（尺寸階層、色彩節奏、單一焦點、留白對比、形狀帶語意）。
  部分生效過，但那次同時改了多個變因，無法歸因。
- 指定具體媒材（risograph、針筆製圖等）。**已撤回**：799px 下紙紋與筆觸看不見，
  只會壓低對比度傷害標籤可讀性。資訊圖的「媒材」等價物是字重、線寬、圓角半徑、
  有無圖示、留白比例。
